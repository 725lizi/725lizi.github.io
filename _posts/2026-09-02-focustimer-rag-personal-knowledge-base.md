# FocusTimer3 接大模型实战（四）：给 App 装一个“只读过我笔记”的 AI

> 这是系列第四篇。第一篇《[项目复盘](./2026‑08‑23‑focustimer‑review.html)》让 App **能跑**；第二篇《[重构实战（二）](./2026-08-30-focustimer-refactor-engineering.html)》让它**结构清晰、测得全**，并埋了“可替换的 AI 接口”；第三篇《[流式与降级（三）](./2026-09-01-focustimer-llm-streaming-fallback.html)》把大模型接进来，做到断网也不崩。这一篇解决一个更本质的问题：**通用大模型根本没读过我的笔记，怎么让它基于“我自己的数据”回答？** 答案是 RAG。
>
> 项目源码：[https://github.com/725lizi/FocusTimer](https://github.com/725lizi/FocusTimer)
> English Version: [On-Device RAG Personal Knowledge Base (IV)](./2026-09-02-focustimer-rag-personal-knowledge-base-en.html)

## 〇、先说结论：这一阶段做了什么

我在手机端给 App 做了一个**个人学习知识库**：把我平时记的专业课 / 英语 / 高数笔记切块、转成向量存在本地；提问时先从自己的笔记里**检索**出最相关的几段，再让大模型**只依据这几段**回答，并标注引用了哪几篇笔记。笔记里没有的内容，它会诚实说“没找到”，而不是瞎编。

| 环节 | 具体做法 | 关键点 / 靠什么保证正确 |
|---|---|---|
| 中文切块 | 按句末标点切句、贪心装箱，每块≤220字、相邻重叠30字 | 纯逻辑 `TextChunker`，8 个单测覆盖硬切/重叠/空串 |
| 向量化 | OpenAI 兼容 `/embeddings`，默认 BGE 中文模型，每块 1024 维 | 厂商可换；维度校验、批量≤16、解析容错，共 19 个单测 |
| 本地检索 | 内存向量库做余弦相似度，降序取 Top5 | 纯逻辑 10 个单测；个人量级毫秒级、完全离线 |
| 持久化 | 关系库新增 `rag_vector_chunk` 表，向量以 JSON 落盘 | 重启 hydrate 回内存；同一来源先删后写，原子重建 |
| 防幻觉 | 相似度闸门 + 字符预算 + “只准用材料”的提示词 | 纯逻辑 `RagQaPlanner` 10 个单测，区分 grounded / no_evidence |
| 整体质量 | 全项目累计 **168 个单元测试**（本阶段新增 60） | 纯逻辑离线测，联网薄层走真机 |

## 一、先想清楚：为什么是 RAG，而不是微调 / 直接把笔记塞进提示词

大模型本身是“读过公开互联网、但没读过我手机笔记”的。要让它用到我的私有数据，常见有三条路，我先做了取舍：

- **微调（Fine-tuning）**：把笔记拿去继续训练模型。代价是要算力、要批量数据、模型更新慢，而且我只是想“查我的笔记”，不是想改变模型的行为方式——杀鸡用牛刀，端上更不可能做。
- **全量塞进提示词（长上下文）**：每次提问把所有笔记拼进 prompt。笔记一多就超过模型上下文长度、又慢又贵，还会“注意力稀释”，模型抓不到重点。
- **RAG（Retrieval-Augmented Generation，检索增强生成）**：先用检索把“和这个问题最相关的几段”捞出来，只把这几段连同问题交给模型。**检索负责找到依据，生成负责组织语言**，数据更新只要重建索引、不用动模型。

对一个个人学习 App，RAG 是唯一又轻、又新、又能解释清楚的方案。它的本质用大白话说就是：**开卷考试——模型是考生，我的笔记是课本，检索是快速翻到相关那几页，答案必须能在这几页里找到出处。**

## 二、一个容易踩的选型坑：DeepSeek 根本不做向量化

RAG 有两类模型调用，很多人会误以为“用一个大模型全包了”：

1. **Embedding（向量化）模型**：把一段文字变成一串数字（向量），用来算“语义像不像”，它**不生成文字**；
2. **Chat（对话）模型**：根据材料和问题生成回答。

我动手前先查证了官方文档：**DeepSeek 只提供对话补全接口，并不提供 embedding 接口**。所以正确的组合是“**聊天用 DeepSeek、向量化另选一个 OpenAI 兼容服务**”。我把向量化客户端写成标准的 OpenAI 协议（`POST /embeddings`，请求 `{model, input}`、响应 `data[].embedding`），默认用硅基流动的中文模型 `BAAI/bge-large-zh-v1.5`（中文检索效果好、国内直连、个人有免费额度），将来想换智谱、阿里百炼，只改配置里的地址和模型名，客户端一行不动：

```typescript
static readonly EMBED_BASE_URL = 'https://api.siliconflow.cn/v1';
static readonly EMBED_PATH = '/embeddings';
static readonly DEFAULT_EMBED_MODEL = 'BAAI/bge-large-zh-v1.5';
static readonly EXPECTED_DIM = 1024;   // 该模型固定输出 1024 维，用来校验返回合法性
static readonly MAX_BATCH = 16;        // 一次最多向量化 16 段，避免请求体过大
```

> 这是一个可以和面试官聊的决策：**先核实能力边界，再用“面向协议而非面向厂商”的方式把可变项关进配置**，避免把第三方 SDK 焊死在业务里。另外，向量化 Key 和聊天 Key 我用两个独立的沙箱 preferences 分开存，互不影响。

## 三、总体数据流：两条流，一个共享存储

![FocusTimer3 端侧 RAG 数据流图](/assets/focustimer-rag-flow-zh.svg)

- **索引流（笔记变化 / 手动重建时跑一次）**：本地未加密笔记 → 中文切块 → 分批向量化（联网）→ 块与向量对齐组装 → 同时写进内存库和关系库。
- **问答流（每次提问）**：问题加 BGE 前缀 → 查询向量化（联网 1 次）→ 在**本地内存库**做 Top-K 余弦检索（离线、毫秒级）→ 防幻觉规划 → 有依据就让 DeepSeek 流式作答并附来源，没依据就诚实声明。

我刻意把“重建知识库”做成**手动按钮**而不是“一保存笔记就自动联网索引”：省流量和免费额度、弱网下更稳、演示时节奏可控；并且**加密笔记一律不索引**，从源头保护隐私。

## 四、中文切块：为什么不能按固定字数硬切

向量化和检索的基本单位不是“整篇笔记”，而是“块（chunk）”。块太大，一段里混了多个主题、向量语义被稀释；块太小，又会把一句话拦腰切断、语义残缺。英文天然有空格分词，中文却没有，而且我笔记里大量是“。；！？”这样的句末标点，所以切块策略必须贴合中文：

1. 先按句末标点切成句子（保留标点）；
2. 贪心装箱：往当前块里加句子，不超过 220 字就继续，超了就另起一块；
3. 相邻块保留 30 字**重叠**，避免正好卡在切块边界上的知识点被劈成两半后两边都检索不到；
4. 遇到完全没标点的超长串，再按“窗口=220、步长=220−30”硬切兜底，保证**不丢字、不死循环**（重叠被收敛到 `[0, maxChars-1]`，步长绝不会是 0）。

```typescript
static readonly DEFAULT_MAX_CHARS = 220;
static readonly DEFAULT_OVERLAP_CHARS = 30;
// overlap >= limit 时强制收敛，防止步长为 0 造成死循环
```

这部分和网络、设备完全无关，我把它写成纯函数，用 8 个单测喂“正常多句、超长无标点、空串、重叠越界”等输入锁死——切块是检索质量的地基，地基必须离线就能证明是对的。

## 五、向量化客户端：把“不可信的网络返回”挡在门外

向量化是本阶段唯一的批量网络请求，我在客户端里做了几件工程上的事：

- **分批**：按 `MAX_BATCH=16` 把块分组请求，避免一次请求体过大被网关拒绝；
- **维度校验**：每段向量必须正好是 1024 维，多了少了都判为非法返回，绝不让脏数据进库；
- **查询前缀**：BGE 中文模型官方推荐给“查询”加一句指令前缀、给“被入库的文档块”不加，实测能提升中文匹配，我把这条规则收进配置方法：

```typescript
static buildQueryText(rawQuery: string, isQuery: boolean): string {
  const q = rawQuery.trim();
  // 只有“问题”加前缀，文档块不加
  return isQuery ? RagConfig.BGE_QUERY_INSTRUCTION + q : q;
}
```

- **解析容错**：网络返回的 JSON 可能缺字段、data 顺序和请求顺序不一致，解析器（`EmbeddingParser`，9 个单测）负责安全取值、按 index 归位、非法就报错而不是崩。

## 六、本地向量检索：个人量级，为什么“暴力遍历”就是最优解

### 6.1 余弦相似度：用方向衡量“语义像不像”

每段文字是一个 1024 维向量，两个向量夹角越小、方向越一致，语义越接近。余弦相似度就是它们夹角的余弦，范围 −1~1，越接近 1 越相关：

```typescript
function cosine(a: number[], b: number[]): number {
  let dot = 0, na = 0, nb = 0;
  for (let i = 0; i < a.length; i++) { dot += a[i]*b[i]; na += a[i]*a[i]; nb += b[i]*b[i]; }
  const d = Math.sqrt(na) * Math.sqrt(nb);
  return d === 0 ? 0 : dot / d;
}
```

检索时拿问题向量和库里**每一块**算一次余弦，丢掉负相关（方向相反）和维度不符的，按分数降序取前 5（Top-K，K=5）。

### 6.2 为什么不引入专门的向量数据库

工业级 RAG 动辄百万、亿级向量，需要 ANN（近似最近邻）索引如 HNSW 来换速度。但**个人笔记是多大规模？** 假设 200 篇笔记、每篇切成 10 块，也才 2000 块。这个量级下，精确的暴力遍历既简单又准，根本不需要近似索引。我用等价算法在开发机 Node 上实测（口径：只测本地切块与余弦检索，不含任何网络）：

| 操作 | 规模 | 平均耗时 |
|---|---|---|
| 一篇笔记切块 | 2000 字 → 10 块 | 0.14 ms |
| 本地 Top5 余弦检索 | 200 块 × 1024 维 | 0.17 ms |
| 本地 Top5 余弦检索 | 500 块 × 1024 维 | 0.45 ms |
| 本地 Top5 余弦检索 | 1000 块 × 1024 维 | 1.07 ms |
| 本地 Top5 余弦检索 | 2000 块 × 1024 维 | 2.40 ms |

也就是说，哪怕攒到两千个知识块，本地检索也只要两三毫秒、**完全离线、不花流量**；整条问答里真正需要联网的只有“问题向量化”和“大模型生成”两次往返。这是一个明确的**复杂度与规模匹配**决策：在数据规模撑爆线性扫描之前，不引入自己都维护不动的重型组件——YAGNI。

我在代码里加了轻量计时埋点（统一前缀 `[RAG-Perf]`，在 DevEco 的 HiLog 里可过滤），真机走查时实测了联网这一段（模拟器、硅基流动 BGE + DeepSeek，2026-09-02）：

| 真机阶段 | 规模 / 结果 | 耗时 |
|---|---|---|
| 重建知识库（读笔记+切块+向量化+落盘） | 1 篇笔记 / 2 块 | 735 ms |
| 问题向量化（联网）+ 本地检索 + 规划 | 命中 2 段，mode=grounded | 464 ms |
| 点发送 → 第一个字（TTFT） | —— | 1327 ms |
| 整段回答生成完成 | 141 字 | 2105 ms |

对照上面的离线表可以清楚看到耗时分布：**本地切块/检索是亚毫秒到毫秒级，用户感知到的等待几乎全部来自两次网络往返**；问题向量化加本地检索规划只用 464ms，1.3 秒蹦出第一个字、2.1 秒出完整答案，配合流式逐字显示体验是流畅的。这次真机日志里 `mode=grounded, used=2` 也直接证明了答案确实是从“我自己的 2 段笔记”里找到依据生成的，而不是模型的通用泛答。

### 6.3 内存库 + 关系库：单一数据源，重启不丢

内存里放一份 `VectorStore` 供检索（快），关系库新增 `rag_vector_chunk` 表把向量以 JSON 文本持久化、并给 `source_id` 建索引（重启不丢）。App 启动时把库里的数据 hydrate（装载）回内存。对外只暴露一个门面 `RagRuntime`，**索引写入和问答检索走同一份数据**，避免“写的地方”和“读的地方”各存一份导致不一致。重建某篇笔记时“先删该来源旧块、再写新块”，做到原子替换、不会重复命中同一篇。

## 七、防幻觉：这个项目真正的壁垒

RAG 最容易翻车的地方不是“检索不到”，而是**检索到一点边角料，模型就顺着它编出一堆笔记里根本没有的东西**。我用一个纯逻辑规划器 `RagQaPlanner` 在“调用大模型之前”先做三道闸：

1. **相似度闸门（AnswerDecider）**：最高分都低于 0.2，直接判 `no_evidence`（没有靠谱依据），根本不假装检索成功；

```typescript
static readonly DEFAULT_MIN_SCORE = 0.2;
static decide(scored: ScoredChunk[], minScore = 0.2): QaMode {
  if (scored.length === 0 || scored[0].score < minScore) return 'no_evidence';
  return 'grounded';
}
```

2. **字符预算（ContextBuilder.fitBudget）**：模型上下文有限，命中材料按相关度从高到低装、累计到 1200 字就停（至少留 1 条），装不下的低相关材料果断舍弃；
3. **来源聚合 + 提示词约束**：同一篇笔记命中的多个块合并成一条引用（界面上显示一个蓝色来源标签），同时用系统提示词“把模型关进材料里”：

```typescript
static readonly SYSTEM_GROUNDED =
  '你是用户的专属学习助手，只能根据下面提供的「个人学习材料」回答问题。' +
  '1）不要编造材料里没有的事实；2）材料不足就明确说“你的笔记里没有足够相关内容”；' +
  '4）凡用到某条材料，在句末标注编号，如[材料1]。';
// 无依据时：先声明“没在你笔记里找到”，再给明确标注为“通用建议”的回答，且不得假装引用笔记
```

于是系统有两种诚实的终态：**grounded（有据，回答附来源）** 与 **no_evidence（无据，先声明再给标注清楚的通用建议）**。注意第二道、第三道是“双保险”——就算阈值判断有偏差，提示词仍然约束模型不许编。界面上每一条 AI 回答下面都会列出它到底引用了哪几篇笔记，**可追溯、可点开核对**，这正是“开卷考试要有出处”的体现。

## 八、可测性：168 个单测，新增的 60 个投在哪

延续前几篇“纯逻辑抽离、设备层做薄”的纪律，本阶段新增 60 个离线单测：

| 纯逻辑模块 | 测什么 | 用例数 |
|---|---|---|
| `TextChunker` | 多句装箱、超长硬切、重叠收敛、空串、不丢字 | 8 |
| `VectorMath` | 余弦方向、零向量、正交、维度不符 | 10 |
| `EmbeddingParser` | 正常解析、缺字段、乱序归位、非法维度 | 9 |
| `VectorStore` + `VectorRetriever` | 增删、Top-K、负相关过滤、空库 | 10 |
| 索引流水线（组装/编解码/分批/持久化） | 块向量对齐、原子重建、JSON 往返、分批边界 | 13 |
| `RagQaPlanner`（预算/闸门/引用聚合/提示词） | grounded/no_evidence、预算截断、同篇合并 | 10 |

真正联网的 `EmbeddingClient`、`RagQaService` 薄到只做“发请求 + 调已测纯函数 + 回调”，靠真机走查。**测试投在“纯逻辑、易出错、可离线复现”的地方回报率最高**——这套取舍我能对每一层说清楚为什么，而不是机械追求覆盖率数字。

## 九、真机踩的两个 UI 坑（都值得讲给面试官）

真机走查时连续遇到两个界面问题，和算法无关，但很能体现声明式 UI 的理解：

1. **笔记编辑页没有返回键**：编辑长笔记时内容把底部导航挤出了首屏。修法是在编辑态的顶部标题栏条件渲染一个“‹ 返回”，退出编辑但不清草稿。
2. **知识库问题输入框点不动、无法输入**：最初我给 `TextInput` 写了 `.enabled(!this.busy())`，把一个**自定义方法调用**绑给通用属性。ArkUI 的界面刷新靠渲染时直接追踪 `@State` 变量，**追踪不到藏在方法内部的状态读取**，初次渲染就可能把输入框误判成禁用。我先改成显式 `@State isAsking` 仍不稳定，最终对照项目里能正常输入的同款布局，**直接移除 `enabled` 绑定**（生成中防重复发送在逻辑层判断即可）才彻底解决。

> 沉淀出的规则：**声明式 UI 的 `if` / 属性绑定里，条件只直接用 `@State` 或常量表达式，不调自定义方法**；需要组合判断时，在状态变更点算好、存进一个显式状态。这也是为什么“找一个项目里已验证可用的同款组件对照”往往比对着文档空想更快定位问题。

## 十、面试视角：这部分可能被怎么追问

**Q1：RAG 和微调、长上下文塞原文有什么区别，你为什么选 RAG？**
A：微调是改模型能力，成本高、更新慢，不适合“查私有笔记”；长上下文塞全部笔记会超长、又慢又贵且注意力稀释；RAG 只检索最相关的几段交给模型，数据更新只需重建索引、轻量可解释，对个人 App 是规模与复杂度最匹配的方案。

**Q2：embedding 模型和对话模型是一个吗？**
A：不是。embedding 负责把文字转向量、不生成文本；chat 负责生成。我查证过 DeepSeek 不提供 embedding，于是聊天用 DeepSeek、向量化用 OpenAI 兼容的 BGE 中文模型，客户端面向协议编程，换厂商只改配置。

**Q3：中文切块为什么要重叠？块大小怎么定？**
A：怕知识点正好被切块边界劈开、两边都不完整而漏召回，所以相邻块重叠 30 字；块上限 220 是“主题尽量单一”和“语义尽量完整”的折中，无标点超长串再硬切兜底并保证步长不为 0、不丢字。

**Q4：你用了什么向量数据库？为什么？**
A：没有用专门向量库。个人笔记撑死两千块，实测 1024 维下 2000 块暴力余弦检索约 2.4ms、完全离线；ANN 索引（如 HNSW）是为百万亿级准备的，这个规模引入它纯属过度设计。这是按数据规模做的明确取舍，将来量级上来再演进。

**Q5：RAG 怎么防幻觉？**
A：三道闸——检索后先看最高相似度，低于 0.2 判无依据；有依据则按 1200 字预算只装最相关材料；再用系统提示词强制“只用材料、不足就明说、引用标编号”，界面列出可核对的来源标签。无依据时进入 no_evidence 终态，诚实声明而不是硬编。

**Q6：向量存哪、重启怎么办、怎么保证读写一致？**
A：内存 VectorStore 供检索、关系库 rag_vector_chunk 表以 JSON 持久化并给 source_id 建索引，启动 hydrate 回内存；对外只有 RagRuntime 一个门面，索引写入和问答检索共享同一数据源；重建某篇先删后写做原子替换，避免重复命中。

**Q7：为什么有的模块单测多、联网模块不怎么测？**
A：切块、向量运算、检索、规划这些纯逻辑易出错且能离线复现，所以高覆盖；联网薄层只做收发和转发，逻辑都已下沉并测过，靠真机走查，硬造 mock 价值低。这是有意识的测试投入取舍。
