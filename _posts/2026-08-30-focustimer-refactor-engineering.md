# FocusTimer3 重构实战（二）：把“能跑”的鸿蒙 Demo 重构成工程上挑不出毛病的版本

> 这是 FocusTimer3 系列的第二篇。第一篇《[FocusTimer3 鸿蒙专注计时器｜ArkTS 项目复盘](./2026‑08‑23‑focustimer‑review.html)》讲的是“怎么从零做出一个**能跑**的 App”；这一篇讲的是另一件事——怎么把它重构成一个**结构清晰、改得动、测得全、工程上挑不出毛病**的版本，为下一阶段接入真正的大模型打地基。
>
> 项目源码：[https://github.com/725lizi/FocusTimer](https://github.com/725lizi/FocusTimer)
> English Version: [FocusTimer3 Refactor in Practice (II)](./2026-08-30-focustimer-refactor-engineering-en.html)

## 〇、先说结论：这一阶段做了什么

这一阶段（我内部叫它“阶段 1：工程打底”）没有加任何新功能，全部在**还技术债**（technical debt，大白话：之前为了先跑起来而欠下的、以后要连本带利还的“将就”）。最终结果：

| 指标 | 重构前 | 重构后 |
|---|---|---|
| 计时首页 `Index.ets` | 782 行的“巨石文件”，UI、计时逻辑、读写数据全混在一起 | 566 行，`build()` 只负责拼装组件 |
| 底部导航栏 | 4 个页面各抄一份，约 166 行重复代码 | 抽成 1 个公共组件，4 页复用 |
| 首页 UI 块 | 全挤在一个文件里 | 拆成 9 个独立组件，共 10 个可复用组件 |
| 计时核心逻辑 | 内联在页面里，离开页面就没法验证 | 抽成纯逻辑 `TimerEngine`，可离线单测 |
| 数据读写 | 两个页面各自直连存储 | 收口到 `FocusSessionStore` 一个入口 |
| 单元测试用例 | 规则引擎仅 14 个 | 全项目 **74 个**（规则引擎 32、计时引擎 18……） |
| 小步提交 | —— | 10 个语义化提交，云端 CI 全程保持绿色 |

下面把每一步“为什么这么做、怎么做、踩了什么坑”讲清楚。

## 一、起点：一个“能跑，但我不敢改”的项目

第一篇复盘写完时，App 在模拟器上是能跑的，但只有我自己知道它有多“脆”：

1. **巨石首页**：计时首页快 800 行，UI 长什么样、秒表怎么走、数据往哪存，全部揉在一个文件里。想改一个小功能，得在几百行里来回翻，还怕牵一发动全身。
2. **重复代码**：底部那排导航栏，在 4 个页面里几乎一模一样地抄了 4 遍。哪天要改一个图标，得改 4 个地方，漏一个就是 bug。
3. **半成品和死代码**：有声明了却没人调用的空方法、有只写了一半的“环境光卡片”（显示的是写死的假数据）、还有零引用的废弃类。
4. **名不副实的命名**：一个本质是“写死模板 + 打分规则”的类，却叫 `AIAnalysisService`（AI 分析服务），周报也叫“AI 周报”。

最关键的是第 5 点：**没有测试兜底，所以我不敢改**。代码能跑 ≠ 代码安全，只要没有自动化测试帮你盯着，任何一次重构都像在没安全绳的高空走钢丝。这就是典型的“技术债”——它不影响今天运行，但会让明天的每一次迭代都越来越慢、越来越怕。

## 二、第一件反直觉的事：先把“AI”两个字删掉

重构的第一个提交，我没有写代码，而是**删名字**：把 `AIAnalysisService` 诚实改名为 `LearningAnalysisService`（学习分析服务），把“AI 周报”改成“学习分析报告”，并在类注释里写清楚：**当前是端侧规则模板，阶段 2 才接真正的大模型**。

为什么要“自曝其短”？因为**命名就是设计，也是承诺**。

- 规则引擎（大白话：程序员提前把“怎么算分、怎么套模板”写成固定逻辑，输入一样输出就一样）和大语言模型（LLM，比如 DeepSeek，能自己生成语言）是两种完全不同的东西。
- 如果为了简历好看继续叫它“AI”，面试官只要追问一句“你这个 AI 用的什么模型、prompt 怎么设计、token 怎么处理”，立刻穿帮，反而被扣“不诚实 / 概念不清”的分。
- 主动说清楚“现在是规则版，我规划了规则 + 大模型的混合架构”，既守住了可信度，又给下一阶段留好了干净的替换点。

这个“替换点”在工程上叫**可替换的接口设计**（大白话：对外只承诺“我能给你一份学习报告”，内部到底是规则算的还是大模型写的，调用方不用知道）。正因为阶段 1 把这层边界划清了，阶段 2 才能做到“有网用 DeepSeek 流式生成、没网自动退回规则版”，而页面一行都不用改。

## 三、分层重构四步走

重构不是“推倒重写”，而是有明确的目标分层。我希望最终依赖方向只能自上而下，下层不知道上层的存在：

![FocusTimer3 分层架构图](assets/focustimer-architecture-zh.svg)

### 3.1 先消灭重复：抽公共底部导航

第一步挑风险最低、收益最确定的动手：把 4 份导航栏抽成一个 `BottomNavBar` 组件，4 个页面统一引用。这一步净减约 166 行重复代码，还顺手补上了笔记页、统计页原本缺失的“分析报告”入口。

> 工程原则：**Don't Repeat Yourself（DRY，消除重复）**。同一段逻辑出现第二次，就该考虑抽公共件——因为重复的每一份都是未来的 bug 温床。

### 3.2 首页组件化：props 向下传、回调向上抛

接着把近 800 行的首页按“视觉块”拆成 9 个组件：计时环、时长档位、科目标签、今日统计、环境光卡片……以最简单的“时长档位选择器”为例：

```typescript
@Component
export struct DurationSelector {
  // 父页面传进来的数据（props，大白话：父组件给子组件的“入参”）
  selectedIndex: number = Constants.DEFAULT_INDEX;
  disabled: boolean = false;
  // 子组件不自己改状态，而是通过回调把“用户点了哪个”抛回父页面
  onSelect: (index: number) => void = () => {};

  build() {
    // ...点击某个档位时：
    .onClick(() => {
      if (!this.disabled) {
        this.onSelect(index);   // 动作上抛，由父页面统一改状态
      }
    })
  }
}
```

这里贯彻的是**单向数据流**（大白话：数据只从父组件往子组件流，子组件想改东西只能“喊”父组件来改，自己不偷偷动手）。好处是：状态在谁那里、什么时候被改，一眼能追到，页面再复杂也不会“数据不知道被谁改了”。拆完后，首页的 `build()` 只剩“把这些组件按顺序摆好”，从 782 行降到 571 行（后续继续降到 566 行）。

### 3.3 把“脑子”从 UI 里抠出来：纯逻辑 TimerEngine

UI 组件化解决的是“长得乱”，但秒表的**运行规则**（开始、暂停、每秒递减、到点提醒、中断计数）还混在页面里。我把这部分抽成一个**纯逻辑类** `TimerEngine`——它不 import 任何 UI、不碰任何系统 API，给同样的输入必得同样的输出：

```typescript
export class TimerEngine {
  static readonly PRESET_DURATIONS: number[] = [300, 900, 1500, 2700, 3600]; // 5/15/25/45/60 分钟
  private currentSecondValue: number;
  private running: boolean = false;
  private pauseCountValue: number = 0;

  start(): void { /* 开始/继续，纯改内部变量，不碰 UI */ }
  pause(): void { /* 暂停，中断次数 +1 */ }
  tick(): void  { /* 每秒走一格：剩余秒数 -1 */ }
  getProgress(): number { /* 由剩余/总时长算进度，供 UI 显示 */ }
}
```

页面里的 `@State`（ArkUI 的响应式状态，大白话：一变就自动刷新界面的变量）只当引擎的“镜像”，每秒从引擎同步一次显示。**为什么纯逻辑最好测？**因为它不需要启动 App、不需要模拟器，new 一个对象、调用方法、断言结果就行，几毫秒跑完。这个引擎我给它配了 18 个单元测试，连“异常退出后从断点接续恢复”都覆盖了。

### 3.4 数据读写收口：FocusSessionStore 仓库层

重构前，首页和统计页都在各自直接读写本地存储，同一套数据有两个入口，以后想改存储方式就得改两处。我加了一个**仓库层**（Repository，大白话：数据的“总服务台”，谁要数据都来这一个窗口，不用知道仓库内部到底把货放哪个货架）：

```typescript
export class FocusSessionStore {
  private static instance: FocusSessionStore | null = null;  // 单例：全局一个总服务台
  private context: Context | null = null;

  public async getAllSessions(): Promise<StudySession[]> {
    if (this.context === null) { return []; }   // 没初始化就安全返回空，而不是崩溃
    try {
      const prefs = await preferences.getPreferences(this.context, 'study_data');
      const raw = await prefs.get('sessions', '[]') as string;
      return JSON.parse(raw) as StudySession[];
    } catch (err) { return []; }                // 读坏了也兜底成空数组
  }
}
```

这里有个刻意的**工程克制**：项目历史上同时存在“轻量 KV 存储”和“关系数据库”两条数据走向，我这一步**只封装、不迁移**——先把入口统一，但不改变数据实际怎么存。因为“统一入口”和“合并双存储”是两个独立的变更，捆在一起做，出了问题根本分不清是谁的锅。小步、每步可验证，才是安全的重构。

### 3.5 顺手修掉真实的质量问题

分层过程中还修了几个“能跑但不对”的隐患：

- **定时器泄漏**：页面里创建了计时器，却在页面销毁（`aboutToDisappear`）时没有对称地停掉。大白话：人都离开房间了，水龙头还开着。我把“创建/销毁”严格配对，避免后台空转耗电。
- **假的环境光卡片**：原来显示写死的数据，改成真正订阅系统的环境光传感器（`AMBIENT_LIGHT`，2 秒采样一次，异常时兜底）。
- **清死代码**：删掉零调用的方法和零引用的废弃类，以及一堆没用到的 import。

## 四、给规则引擎补测试：不写“摆样子”的 happy path

重构有了安全绳之后，我反过来加强这根绳——给规则引擎补测试。这里我刻意不写那种“一切正常时输出正确”的 **happy path**（大白话：只测风和日丽、不测刮风下雨的自嗨测试），而是专攻**边界值**和**分支**（大白话：专挑临界、极端、容易出岔子的输入）。

规则引擎的专注分是三维加权：

```typescript
const durationScore  = Math.min(100, (avgDuration / 45) * 100); // 时长分：以 45 分钟为满分基准
const interruptScore = Math.max(0, 100 - interruptRate * 100);  // 中断分：中断越多越低
let regularityScore = 80;                                        // 规律分：每天时间越稳定越高
const focusScore = Math.round(
  durationScore * 0.4 + interruptScore * 0.35 + regularityScore * 0.25
);
```

围绕它，我把用例从 14 个加到 **32 个**，专门覆盖：空数据、只有一条、跨天重复去重、全程中断（精确 65 分）vs 全程不中断（100 分）、超长时长封顶 95 分、空标签、趋势上升/下降、六个时段的临界值（6 点、21 点整）、番茄时长被钳制在 15~90 分钟、英文术语、停用词过滤、周报环比……

一个细节：云端 CI 环境没有鸿蒙 SDK，跑不了 ArkTS 测试。我先用 Node.js 把这套纯逻辑**等价转译**一遍，把 59 条断言（assertion，大白话：“我断定结果必须等于 X，不等就报错”）真实跑通、把每个期望值锁死，再原样写回鸿蒙的 hypium 测试框架。这样避免了“凭感觉写期望值”，测试是真的能抓错、而不是凑数。

## 五、最值钱的一课：CI 一路绿，本地编译却挂了

这是整个阶段最有收获的部分，也是最适合写进面试故事的一段。

### 5.1 云端 CI 全绿，本地 DevEco 一编译，4 个错误

我每次提交，云端 CI（持续集成，大白话：代码一推上去就自动跑一遍检查的流水线）都显示绿色通过。但当我第一次在本地用 DevEco Studio 完整编译时，直接报了 4 个 ERROR：

**错误 1~3：`Property 'get/put/flush' does not exist on type 'void & Promise<Preferences>'`**

根因是：仓库里的 `this.context` 类型是 `Context | null`（可能为空）。我没先排除“为空”这种情况就去调 `getPreferences`，于是编译器在多个**重载**（overload，大白话：同名方法支持不同传参方式）之间，错误地匹配到了“传回调、返回 void”的那个版本，自然就没有 `.get()` 方法。对照项目里能正常编译的类，我在方法开头加了一道**非空守卫**做**类型收窄**（大白话：先把“为空”的分支挡掉，编译器就能确定后面它一定不为空）：

```typescript
if (this.context === null) { return []; }   // 守卫：先收窄类型，再调用 API
const prefs = await preferences.getPreferences(this.context, 'study_data');
```

**错误 4：`Namespace 'sensor' has no exported member 'AmbientLightResponse'`**

这是我凭记忆写的类型名，而 SDK 里根本不存在。正确做法不是猜，而是直接打开本机 SDK 的**类型声明文件** `@ohos.sensor.d.ts`（`.d.ts`，大白话：SDK 自带的“字典”，写清了每个 API 到底叫什么、参数返回什么类型），查到环境光回调的真实类型是 `sensor.LightResponse`，改过来即可。

### 5.2 失效的测试：该删，还是该补？

主代码编译过后，跑全部单测又冒出 4 个错：一个测试文件 import 了**根本不存在的类** `CardDataBuilder`，连带触发 ArkTS 的 `arkts-no-any-unknown`（鸿蒙强制每个变量写清类型、禁止用 `any` 这种“随便什么都行”的模糊类型）。

我没有图省事把这两个测试删掉（那是“为了绿灯降低覆盖率”，等于掩盖问题），而是正向修复：把原本内联在桌面卡片服务里的格式化逻辑抽成一个新的纯逻辑类 `CardDataBuilder`，让失效测试重新有了真实的被测对象，再把自相矛盾的旧用例重写、补了“补零/向下取整”的边界用例，并显式标注类型消除 `any`。

### 5.3 升华：CI 不是万能的，质量要靠“分层门禁”

这件事让我真正理解了一个道理：**绿色的 CI 不等于能编译、能运行**。因为云端受鸿蒙 SDK 分发限制，我的 CI 只能做“仓库规范校验”（文件编码、分支、提交信息等），它压根没编译 ArkTS 代码。于是我把质量保障明确成一道道**层层递进的门禁**，每道拦住不同的问题：

| 门禁 | 在哪跑 | 主要拦住什么 |
|---|---|---|
| ① 规范校验 | 云端 CI | 编码、分支、提交信息、仓库结构问题 |
| ② 完整编译 + 类型检查 | 本地 DevEco | 类型错误、API 名写错、空值未处理（本次 4 个错就在这层被抓） |
| ③ 单元测试 | 本地 hypium | 逻辑回归、边界分支错误 |
| ④ 模拟器 / 真机 | 设备 | UI、传感器、生命周期等运行时问题 |

另外我给自己立了条规矩：**绝不用 `as any` 之类的强制类型断言去“压制”报错**（大白话：不是把问题修好，而是捂住编译器的嘴让它别喊），那只会把编译期错误拖成线上事故。

## 七、面试官可能怎么追问

**Q1：为什么花一整个阶段重构，而不急着加功能？**
A：因为这个项目是要长期迭代、最终接大模型的作品集，地基不牢，后面每加一个功能都在还利息。我先用一阶段把分层、测试、命名做扎实，阶段 2 接 AI 时才能做到“加一个实现层、页面零改动”。这是主动的工程决策，不是返工。

**Q2：纯逻辑层和 UI 的边界怎么划？**
A：凡是“给定输入就能算出输出、不需要界面和设备”的都下沉为纯逻辑（计时规则、打分、格式化），UI 只负责渲染和把用户动作回传。判据很简单：这段逻辑能不能不启动 App、new 个对象就测？能，就该抽出来。

**Q3：仓库层为什么不直接把两套存储合并成一个？**
A：因为“统一入口”和“合并存储”是两个不同风险级别的变更，捆在一起出问题无法定位。我先统一入口、保持数据走向不变，把合并留到有测试兜底之后，这是小步可回退的重构策略。

**Q4：CI 都绿了，为什么本地还会报错？你会怎么改进 CI？**
A：因为云端 CI 受鸿蒙 SDK 限制只做了规范校验，没有编译。这让我意识到每条流水线的“覆盖边界”必须说清楚。后续可以在 CI 里接入带鸿蒙 SDK 的构建镜像做云端编译，把第②道门禁也自动化；在那之前，本地完整编译是必须人工守住的一关。

**Q5：规则引擎和 AI 到底什么关系？**
A：规则引擎是确定性的兜底实现，大模型是增强实现，两者实现同一套“产出学习报告”的接口。有网用 DeepSeek 流式生成更自然的内容，断网自动回退规则版保证功能永远可用——这正是阶段 2 要做的事。

## 八、下一步：阶段 2，接真正的大模型

地基打好后，下一阶段我会：①接通 DeepSeek API，**流式**（streaming，大白话：像 ChatGPT 那样一个字一个字往外蹦，而不是干等一整段）生成学习周报；②做好**无网降级**，断网时自动退回这一阶段打磨好的规则引擎；③把密钥管理、加载态、错误重试这些工程细节补齐。届时这篇里埋的“可替换接口”就会真正兑现。
